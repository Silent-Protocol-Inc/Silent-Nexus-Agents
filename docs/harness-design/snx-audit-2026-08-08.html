Findings

Severity reflects operator safety, contract drift, and likelihood of a wrong decision—not code style.

H-01 · Approval UI hides isolation strengthRESOLVED 2.16.5

Principles: H-2 visible boundary; H-5 safety is legible; Constitution 2.3.

Before: CLI and TUI reduced action isolation to “active” or “NOT isolating this action”, hiding the material difference between strong containment, approval-only host execution, and path-validation-only execution.

After: each attended approval carries the backend's IsolationReport into presentation and shows its stable level plus filesystem and network descriptions. If that specific action is not isolated, the warning says so alongside the configured level. Existing one-time-only and persistent-grant rules are unchanged.

Benchmark influence: Claude's trust gate was the strongest observed consent surface because it named the exact workspace and concrete read/edit/execute capabilities. SNX adopts that specificity while going further on runtime containment.

M-01 · CLI and TUI command contracts still have two authorsMEDIUM

Principles: H-4 one control plane; Constitution 4.3 one authoritative home.

The app registry calls itself the single command table and owns slash-command metadata, while the CLI separately defines the public Clap enum, aliases, flags, and usage. The registry has non_interactive, but no checked derivation proves it matches the Clap surface. This is a drift risk even though current registry tests pass.

Evidence: registry.rs:1–7; registry.rs:99–117; cli.rs:36 onward.

Recommendation: make the registry the source for command identity, aliases, help, and surface availability, then add a parity test that walks Clap’s generated command tree and compares it with the registry. Keep only surface-specific argument types in Clap.

M-02 · Doctor reports failed checks but exits successfullyMEDIUM

Principles: H-7 evidence status; Constitution 2.7 evidence outranks narration.

snx doctor --deep --json returned exit code 0 while its JSON contained failed checks for local model servers and automatic terminal isolation. The output is honest, but automation sees success unless it parses the payload. A readiness command should make the machine-readable success contract explicit.

Observed: local model servers: ok=false; automatic terminal isolation: ok=false; process exit 0.

Evidence: doctor JSON rendering; doctor human rendering.

Recommendation: define severity classes. Return non-zero for blocking readiness failures, retain zero for informational warnings, and emit an aggregate field such as status: "blocked" with a documented exit mapping.

L-01 · JSON output is intentionally partial, but the contract is underspecifiedLOW

Principles: H-4 shared semantics; Constitution III stable machine output.

The global flag says “machine-readable JSON where supported”. Many commands support it, while state-setting or interactive commands still render human reports. That is reasonable, but the boundary is not discoverable from help or a generated capability table.

Evidence: global flag wording; mixed handler behavior.

Recommendation: expose json: supported|unsupported|events in the command registry and make snx help show it.

M-03 · TUI rendering contract is currently redMEDIUM

Principles: H-4 shared control plane; H-6 continuity; Constitution V verification floor.

The locked workspace test run produced eight failures in nexus-tui render tests, including diff-card status, narrow-terminal activity, tool-card lifecycle, error/limit markers, mobile-landscape elapsed time, reduced-motion rendering, final-answer distinction, and timeline/context snapshots. These are precisely the surfaces that carry the harness’s operational evidence.

Resolved in 2.16.4: environment-independent lifecycle assertions now accept the real ASCII or geometric terminal tier, responsive snapshots were intentionally rebaselined after visual inspection, and focused-layout coverage was added.

Verification: 245 passed, 0 failed, 2 visual-only tests ignored in nexus-tui; the full locked workspace test suite also passed.

Best deletion lesson

OpenCode mini proves a launch surface needs little more than a prompt, current mode, and one route to commands. SNX's focused view should stay this calm.

Best evidence lesson

Codex's typed JSONL lifecycle makes attempted, running, completed, and verified work easy to distinguish. SNX should preserve its durable timeline while suppressing repetitive incidental diagnostics.

Best consent lesson

Claude's trust gate names the exact workspace and capabilities. SNX 2.16.5 applies the same concreteness to isolation, filesystem, and network at every approval.

Strongest warning

Hermes and customized Claude show two forms of clutter: permanent chrome and procedural event volume. Neither should be copied into SNX.

Run integrity: one execution per harness; fixed 100×30 launch capture; identical fixture hashes; model APIs required network; OpenCode and Hermes could not authenticate their selected free routes. Results are observations, not a general model leaderboard.

Recommended order of work

  1. Standardize provider recovery: every authentication, quota, and unavailable-model error should name the failed route and one concrete recovery action, without leaking raw provider payloads.
  2. Define doctor’s exit contract: make readiness usable by CI and operators without requiring ad hoc JSON parsing.
  3. Close command parity: generate or validate the Clap surface from the app registry.
  4. Run a consent study: measure time-to-correct-consent for strong, host-approval, and path-validation-only actions at 80×24 and 100×30.
  5. Repeat the fixture: rerun free OpenCode and Hermes routes after authentication so their model-result score is no longer blocked by environment state.
